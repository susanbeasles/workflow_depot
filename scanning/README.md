# Local scanner checkpoint

This source has working local adapters for Gitleaks 8.30.1 and Semgrep 1.180.0, a complete filesystem inventory reader, and an npm package-lock v3 integrity verifier. It is **not** a qualified full application scan. `policy.json` remains unqualified and required unavailable categories prevent any successful full report. No application repository was scanned or uploaded during development; real scanner runs used generated temporary fixtures only.

## Execution and trust

`scripts/install-scanners.py` downloads Gitleaks from its official GitHub release and verifies both archive and extracted executable SHA-256. Semgrep and all 65 Python dependencies are pinned by version and hash in `semgrep-requirements.txt`; each downloaded wheel was independently compared with official PyPI release metadata before installation. The installer uses only wheels, hash-required downloads, and offline installation. Public release checksums establish the artifact integrity used here; this is not a claim of a separately verified release signature or build attestation.

`tool-lock.json` pins rule bytes, executable bytes, and the Semgrep interpreter and complete installed site-packages digest (including semgrep-core). Those runtime pins describe the temporary qualification installation under `/tmp/workflow-depot-scanners`; a different Python/runner installation fails closed and needs its own reviewed qualification. They are not automatically replaced by hashes of whatever happens to be installed. The installer does not run application code. Runtime files are checked again before scanner invocation.

The adapters invoke fixed recognized commands without a shell or inherited credentials. They bound execution time and combined stdout/stderr, kill the subprocess group on timeout, disable Semgrep metrics/version checks, use local pinned rules only, and never request online secret validation. The source has no vendor token or upload endpoint. Raw findings and stderr are not returned; failure is a fixed code. Gitleaks reports are redacted before parsing. This is a CLI-level offline configuration, not a newly implemented network sandbox.

## Supported and unavailable coverage

Gitleaks uses its pinned built-in rules through the depot TOML configuration, overriding app rule files, ignore files, and `gitleaks:allow` comments. Semgrep uses two depot-owned JavaScript/TypeScript rules for dynamic `eval` and direct `child_process.exec`. This small ruleset proves the adapter execution contract; it is not a comprehensive SAST ruleset or a substitute for SonarQube standard quality rules.

Both adapters verify the complete inventory digest and current file contents before and after scanning. Any per-tool exemption must be an exact path and reason from independently trusted policy. They never relabel a filtered inventory as a complete inventory. Hidden/cache files are not implicitly ignored. Binary/invalid-UTF-8 files, archives, and symlinks are rejected unless explicitly exempted for that tool: Gitleaks can silently skip binary files, so zero findings is insufficient to claim those bytes were scanned. Semgrep must report every selected file as scanned; parse errors, skipped languages, timeouts, unsupported switches or missing tools block.

The inventory includes hidden files, cache inputs, binary artifacts and symlink records, hashes regular-file bytes, bounds total bytes/file count, and rejects special files, escaping/directory symlinks and changing files. This is integrity inventory, not malware detection. The npm verifier checks the independently pinned lockfile hash, every locked package version and SHA-512 cached-archive integrity, and every installed tree against an independently trusted tree digest; it rejects extra/missing packages. The expected tree/archive mappings must come from reviewed policy or verified cache provenance, never an app-supplied manifest. Yarn locks, workspace/link dependencies, other package managers, and incomplete artifact provenance remain unavailable in this verifier.

Required categories currently without qualified adapters are vulnerability/SCA, authorized isolated DAST and pentest, malware, SonarQube quality, workflow/IaC, SBOM, IAST, fuzzing, RASP, ASVS/WSTG, and provenance. Qualys, Wiz, Trivy, ClamAV and CodeQL are not installed or claimed as run. Dynamic testing may only use source-owned authorized isolated targets, never PR-provided URLs. The full report validator requires the mandatory categories, exact tool versions/rule digests, current databases where applicable, exact inventory coverage/exemptions, and the required pinned SonarQube standard ruleset. Missing evidence stays unavailable, not passed.

Application stack classification is also unqualified: the current full-scan producer records JavaScript/TypeScript extension hints and has no independent framework discovery. Those hints are not proof that a mixed stack is supported. The policy must remain unqualified until independently verified language/framework evidence exists. No central framework/runtime registry is introduced to hide this gap.

## Workflow and report

The existing `full-scans` job checks out the reviewed depot scanner revision and exact admitted application SHA separately. It restores the same application environment bytes only after matching the setup job digest, runs no app script, and receives no OIDC or inherited secrets. It reads the admitted tree/policy digest from source-admission outputs. The source-owned `REVIEWED_DEPOT_SHA` sentinel and unqualified scanner policy block activation until reviewed configuration exists. A workflow at revision B may pin scanner runtime A; no file inside A is required to contain its own commit SHA.

The app archive remains untrusted even when its digest matches: app setup can create malicious archive contents. Scanner restoration therefore uses `scripts/restore-environment.py`, not the app's tar executable. It bounds compressed/expanded bytes and member count, stages only regular file data in a fresh private directory, checks the entire member set and destination before overlay, rejects Git metadata, traversal, duplicate names, hardlinks, special files and existing symlink/hardlink aliases, and writes through no-follow directory file descriptors with atomic file replacement. Internal cache symlinks are allowed only to regular files in the same archive and are created last. Existing trusted-scanner siblings cannot be reached through a candidate checkout symlink. All malicious archive tests use generated local fixtures.

On complete success only, `scripts/full-scans.mjs` writes canonical `scan-report.json` (maximum 32 MiB), emits its raw SHA-256, and the standard Actions artifact step publishes the uniquely named repository/run/attempt/S artifact with overwrite disabled. Native outputs are only `scan_report_digest` and `scan_artifact_id`. The shared reviewer downloads that report as data, never the application CI environment. `src/scan-report.mjs` revalidates source coordinates and full report coverage against an independently retained candidate and scanner policy. A report does not authenticate itself.

No full report has been produced or uploaded; required unsupported tools and uncommissioned policy prevent that.

## Verification

Run ordinary synthetic tests with `node --test test/scan-adapters.test.mjs test/scan-report.test.mjs`.

The separate actual-tool qualification is `node --test test/scanner-qualification.mjs`. It requires the verified temporary tool installation and fails if tools/pins are missing; it does not silently skip qualification. It scans only generated clean and intentionally failing hidden JavaScript fixtures, including attempted inline suppression and ignore files. The initial actual Gitleaks binary-file false-coverage observation is now covered by a deny-before-execution regression. No scanner is aimed at the source checkout.

The existing temporary qualification tree holds Gitleaks at `/tmp/workflow-depot-scanners/gitleaks/gitleaks`; the installer for a fresh workflow writes it directly at `/tmp/workflow-depot-scanners/gitleaks`. Both use the same fixed executable hash. Semgrep's path and fixed runtime/interpreter pins are identical. Neither layout is a newly commissioned production runner.

The pinned version does not accept every flag shown by the current rolling documentation; the synthetic actual-tool tests determine supported invocation.
